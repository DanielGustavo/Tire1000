# Listagem de temas + filtro (desktop)

Type: prototype

Blocked by: 04

## Question

Adaptar a listagem de temas construída na ticket "Listagem de temas + filtro (mobile)" para desktop, usando o frame "Temas" (nó `195:1437`, canvas Desktop `106:1830`) como referência. Confirmar se o filtro por eixo continua em modal no desktop ou se vira um painel lateral/inline (mais espaço disponível) — checar com `get_design_context`.

## Answer

`frontend/src/pages/themes/themes.tsx` ganhou classes `lg:` (mesmo padrão das tickets 08/09): teto `lg:mx-auto lg:max-w-[1280px]` escopado à própria página (não no `AppLayout` compartilhado), padding horizontal `lg:px-10` nas 3 seções (título/voltar, busca+filtro, grid), e a lista de temas troca de coluna única (`flex-col`) pra um `grid grid-cols-1 lg:grid-cols-3` batendo com o frame "Temas" desktop do Figma. `ThemeListItem` e `Pagination` foram reaproveitados sem alteração — comparando o dump de `get_design_context` com o código atual de `Pagination.tsx`, os tamanhos (`text-small`/`text-default` bold+underline pra página atual, `IconButton` `size-10`/40px) já batiam exatamente com o frame desktop, então não precisou de ajuste (ao contrário do que a ticket cogitava como possibilidade).

**Filtro por eixo: continua modal, não virou painel lateral/inline.** Chamei `get_design_context` no nó `195:1437` (frame "Temas" completo) e não existe nenhum frame de estado aberto do filtro no Desktop — o frame só mostra o trigger fechado (campo de busca + ícone `sliders-horizontal`, mesmo do mobile) mais uma "Tags List" inline logo abaixo da busca com 3 chips de exemplo ("Cidadania", "Saúde e sociedade", "Meio ambiente", cada um removível). Essa Tags List é o mesmo componente genérico com dado de exemplo que a ticket 04 já tinha encontrado e descartado pro mobile (não é multi-seleção real — o backend só aceita um `topicId` em `GET /themes`), só que reaparece aqui solta na página em vez de só dentro do modal. Não implementei essa fileira de chips inline (nem um chip único pro filtro ativo) pra não reabrir a decisão de multi-seleção sem um usuário ao vivo pra confirmar — a ticket pede pra preservar a decisão da 04 estruturalmente. Como `Modal.tsx` (`components/Modal.tsx`) já cabia no padrão de modal pequeno centralizado do Figma desktop desde a ticket 08 (sem mudança necessária lá também), a opção que muda menos o comportamento existente é manter o `ThemesFilterModal` como está — decisão tomada sem `/grilling` ao vivo (sessão em background), mas de baixo risco por não alterar nenhum comportamento.

**Questão aberta, não resolvida nesta ticket:** `THEMES_PER_PAGE` (definido em `useThemesPage.ts`) continua fixo em 3, igual ao mobile, mesmo o grid desktop tendo 3 colunas — o frame do Figma mostra um grid 3x3 (9 temas/página) com paginação "1 2 3 ... 25". Adaptar o tamanho de página por breakpoint exigiria detectar `lg:` via JS (`matchMedia`, sem precedente no código — só `Select.tsx` usa `window.matchMedia` hoje, pra `pointer: coarse`) e mudaria semântica real de paginação: a página "2" apontaria pra um conjunto diferente de temas em mobile vs desktop, e redimensionar a janela em cima do breakpoint exigiria recalcular `page`/`totalPages` em runtime. Isso é uma decisão de comportamento, não só de layout, então preferi documentar como questão aberta em vez de decidir sem usuário — o grid de 3 colunas hoje só preenche 1 linha por página (nunca fica com linhas vazias, já que 3 itens exatamente enchem 3 colunas). Se o produto quiser bater com a densidade do Figma (9/página em desktop), fica pra confirmar numa sessão com usuário ao vivo.

**QA manual em navegador não foi possível** (mesma limitação das tickets 04/06/07/08/09) — sem ferramenta de automação de browser disponível nesta sessão background. Validado só por `tsc -b`/`oxlint`/`vite build` limpos e `/code-review` (eixo Standards: nenhuma violação, só o smell de valor de pixel mágico repetido já registrado e aceito desde a ticket 08; eixo Spec: 2 achados reais — a seção Answer/entrada no map faltavam no momento da revisão, corrigidas nesta rodada de commit; e o comentário no código sobre `THEMES_PER_PAGE` citava "mesma convenção das tickets 08/09" de forma imprecisa — 08/09 não envolviam grid paginado multi-linha — reescrito pra explicar o trade-off real em vez de invocar precedente que não se aplica).
